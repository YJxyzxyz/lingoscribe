# iOS / Android 发布指南

Git 管理每次发布对应的源码。商店构建、签名、上传和审核流程需在选定应用技术栈并配置开发者账号后接入。

## 版本约定

- 用户可见版本：`MAJOR.MINOR.PATCH`，例如 `1.0.0`。
- 正式提交构建的源码标签：`v1.0.0`。
- 测试候选源码标签：`v1.0.0-rc.1`；下一个候选为 `v1.0.0-rc.2`。
- iOS：记录应用版本和构建编号。
- Android：记录应用版本（`versionName`）和递增构建编号（`versionCode`）。

两端可以分别上线，但必须记录各自的源码标签和构建编号。不要覆盖或移动已经提交商店的标签。
若提交后还需修改源码，应创建新的候选或修订版本标签，并提高对应平台的构建编号。

## 发布步骤

1. 合并本次发布需要的变更，确保工作区干净。
2. 更新应用实际版本配置及两端构建编号，并将 `CHANGELOG.md` 的待发布内容移到对应版本和日期下。
3. 完成当前技术栈的检查、两端构建和真机验证；检查权限、登录、关键业务和升级行为。
4. 提交版本配置和更新日志，给通过验证且实际用于构建的提交创建附注标签。
5. 推送源码和指定标签，将由该标签构建的产物提交到对应商店。
6. 使用下方模板记录构建、提交、审核和上线状态；源码标签只代表发布源码，不代表商店已审核或上线。

以下仅为操作示例，`1.0.0` 应替换为实际发布版本：

```powershell
git switch main
git status
git log -1 --oneline
# 确认版本配置已提交、检查通过且工作区干净后：
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin main
git push origin v1.0.0
```

构建工具接入后，应支持直接从发布标签检出并构建，确保产物与源码一致。
首次初始化仓库不创建发布标签；标签应在实际应用通过发布验证后建立。

## 每次发布记录

复制此模板到 `docs/releases/<版本号>.md`，按实际情况填写；不要写入密码、签名私钥或访问令牌。

```markdown

- 源码标签：
- Git 提交 SHA：
- 发布说明：
- 构建环境 / 工具版本：
- 验证结果：
```

## 线上修复

从受影响版本标签创建修复分支，例如 `git switch -c fix/1.0.1 v1.0.0`。
完成修复、测试和版本配置更新后，按发布步骤创建新的修订版本标签，并将修复合并回 `main`。
商店回退通常需要提交新的构建；Git 回到旧提交并不会自动撤回已上线的应用。
